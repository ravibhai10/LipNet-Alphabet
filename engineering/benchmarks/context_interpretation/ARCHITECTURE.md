# Hybrid context interpretation: proposed architecture

Status: design and offline benchmark preparation only (2026-11-19). No provider integration, model inference, backend launch, or production-state change was performed.

## Existing boundary

The current optional path is a post-processing suggestion service. `app/context_routes.py:36-45` authenticates the actor, requires the `X-Interpretation-Session` bearer token, checks active purpose-specific consent, calls the interpretation service, and rechecks session currency before returning. Session creation, consent, revoke, and termination are separate routes (`app/context_routes.py:71-107`). `app/services/context_sessions.py:58-82` creates an opaque random token and persists its SHA-256 digest; lines 84-107 validate it and grant consent. Participant binding is optional and creation checks the `participants` registry against the same owner (lines 67-71); it does not authenticate the person in front of the camera. Shared collector credentials identify the configured principal only.

`app/services/context_interpretation.py:56-80` bounds request fields and validates ordered, unique Top-K candidates and the original visual result. Only `word` and `expanded` are eligible (lines 89-97, 181-200); `alphabet` and `lrw500` bypass contextual inference. The service scopes cache keys to actor, session, optional verified participant, model, and payload hash (lines 199-208); capacity is 128 entries and TTL is 60 seconds (lines 155-164, 207). Provider output is schema constrained and checked against the candidate list (lines 109-118, 230-239). The visual result remains in `safe_prediction`; a suggestion is separate and requires user confirmation (lines 166-173, 247-255).

The provider is currently fixed to OpenAI Responses API (`app/services/context_interpretation.py:23,33-47,109-137`); this is not a provider-neutral production adapter. Defaults remain disabled unless `LIPNET_LLM_ENABLED=1` and a key is configured (`:100-107`). The service does not automatically retry provider requests. It uses bounded transport concurrency and deadlines (`:24,33-47,119-137,214-229`). The session submission/revocation fence is process-local (`app/services/context_sessions.py:1-5,169-200`) and relies on the supported one-process/one-worker deployment (`engineering/20261117/DEPLOYMENT.md:7,79`). Do not use multiple workers/replicas without a shared fence.

Frontend session tokens are held by the `ContextClient` object in memory (`frontend/src/live-demo/contextInterpretation.ts:31-39`); consent and interpretation calls send the session token in the request header (`:48-80`). UI starts disabled and has explicit consent text naming OpenAI (`frontend/src/workspace/components/ContextInterpretation.tsx:8,87`). Page teardown attempts termination (`:70-73`); a failed termination remains retryable (`:14-19,82`). These user-facing notice/provider semantics must be updated and reviewed before any non-OpenAI provider is used.

`engineering/LLM_CONTEXT.md` documents default-disabled behavior, text-only bounded input and confirmation semantics, but its cache paragraph should be reconciled with the current actor/session/participant key before production provider work; this preparation leaves that existing file untouched. The deployment guide explicitly says Docker has not been executed (`engineering/20261117/DEPLOYMENT.md:97-110`).

## Proposed hybrid design (not implemented)

1. Keep the existing route/session/consent gate as the only entry point. Never accept actor, session, participant, or consent identity from interpretation JSON. Continue to derive the actor from existing authentication and scope the request to the server-resolved session. Do not infer a webcam participant from a collector account.
2. Before integration, replace the hard-coded provider assumption with an internal provider interface that accepts only the already validated text payload and returns a strict `Suggestion`. A server-side, pinned cloud model ID is primary; a single local Ollama model is fallback. Provider selection must not be client-controlled. No automatic retry to the same provider; cloud failure can route once to local. If local is unavailable, fail closed and preserve the visual result.
3. Keep the production feature default-disabled. Enablement requires explicit operator configuration plus the current session-bound consent. The consent notice must identify the cloud provider/model class, data sent, retention/training policy, and local fallback behavior. Obtain renewed consent under a new notice version before sending any payload to a provider not covered by the existing OpenAI notice.
4. Enforce the same strict JSON schema, enum reason, Top-K allowlist, bounded token/output limits, no tools, no media, and no prompt-carried instructions for every adapter. Treat context/history as untrusted data. A valid JSON response alone is not a correct interpretation. Invalid, out-of-candidate, refused, timed-out, or unavailable output becomes abstention/failure; never change `safe_prediction` or auto-apply a suggestion.
5. Preserve consent/revocation fencing around the provider-submission boundary and around result publication. No SQLite write transaction may span inference. A revoked/terminated request may not publish/cache/return a late result. The process-local fence is safe only in the documented single-process deployment.
6. Keep the existing 128-entry/60-second cache policy, actor/session/participant/model/payload isolation, lock-protected operations, and targeted session eviction. Do not add a fallback to the previous or unscoped cache.
7. Record only provider/model/prompt version, outcome class, bounded timing, and non-sensitive counters. Never log token, context, history, raw prompt, pseudonym, or raw provider response. Keep per-provider failure/circuit accounting separate from actor identity where practical.

## Candidate and pricing status

No cloud model is selected or called in this task. OpenRouter's current public collection lists free variants with `$0` model pricing while also describing rate limits and account-dependent limits; exact IDs and restrictions are dynamic and must be pinned and rechecked at execution time ([OpenRouter free models](https://openrouter.ai/collections/free-models), [model catalog](https://openrouter.ai/models?variant=free)). NVIDIA's Nemotron 3 Ultra NIM page currently advertises a free API endpoint, but the endpoint's account, rate, retention, and usage restrictions still require verification for the exact deployment ([NVIDIA NIM model page](https://build.nvidia.com/nvidia/nemotron-3-ultra-550b-a55b)). Baidu states the ERNIE 5.5 Flash Preview API is available through Qianfan, but that announcement does not establish a free API tier ([Baidu ERNIE announcement](https://ernie.baidu.com/release/ernie-5-5-flash-preview/)). Google's Gemini API pricing page describes a free tier for limited model access and separately warns that free-tier data may be used to improve products; the exact eligible model, region, quota and terms must be checked before use ([Gemini API pricing](https://ai.google.dev/gemini-api/docs/pricing)). Therefore none is approved here as an operationally free, privacy-suitable provider.

OpenRouter routing can select different underlying models over time; use an exact pinned variant rather than an unpinned router for any reproducible benchmark. A free price does not mean an appropriate privacy/retention contract. The benchmark must record the provider, exact endpoint/model ID, pricing evidence date, account/region constraints, free quota, retention/training policy, prompt version, and any provider-side changes. Do not send research data until those terms are reviewed and consent notice is appropriate.

## Local hardware observation

Read-only check on 2026-11-19 found Intel UHD integrated graphics, no detected NVIDIA GPU or `nvidia-smi`, approximately 7.7 GiB total system RAM and approximately 0.5 GiB free at check time, and no `ollama` executable. No local model was installed or invoked. Qwen3 4B and optional Qwen3.5 4B are therefore candidates for a future separately approved benchmark only; local inference is **NOT RUN**. Memory availability is time-dependent and must be checked again before any operator-approved local run.

## Review gates before integration

- Resolve and document exact cloud IDs, exact free pricing/quotas, region/account limitations and privacy/retention terms; pin the variant for each run.
- Update purpose-specific consent notice and obtain new consent before any newly named provider receives data.
- Establish an installed, explicitly chosen Ollama model and sufficient available memory; do not download automatically.
- Add adapter-level timeout/cancellation and deterministic mocked tests, including revocation fencing and late-result suppression.
- Test single-process deployment only; if deployment changes to multiple processes, replace the process-local fence with a cross-process atomic mechanism before enabling.
- Obtain separate approval for production provider integration and any live benchmark. This document does not authorize either.
